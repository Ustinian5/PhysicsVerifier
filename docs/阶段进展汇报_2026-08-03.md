# PhysicsVerifier 阶段进展汇报

> 冻结快照：本文只记录截至 2026-08-03 的阶段认识。后续审计已发现 1139 增量验证盲区，并修正了误报证据口径；当前状态以[项目进展](项目进展.md)为准。

汇报日期：2026-08-03

项目目标：检查模型对物理竞赛题的解答，输出可定位、可解释的物理错误诊断。
本人当前主要负责：`unified_rules` 规则库、语义检索链路及相关效果测评。

## 一、本阶段概要

本阶段已完成规则库结构化、语义导航接入、增量更新流程和 20+20 validation 测评，并完成两类 catalog 消融。

当前结论是：1123 条粗化规则库具有明确的错误召回信号，但正确题误报过高；直接扩充为 4875 条规则或硬性使用 runtime metadata，都会显著损失召回。因此当前不应直接扩大为服务器 final-test 实验，下一步应先在 development/合成数据上重新设计通用 precision 层。

## 二、已完成工作

### 1. 统一规则库

- 将 4361 条候选概括为 609 条多样本规则，与 514 条基线规则合并为 1123 条正式规则。
- 构建 189 个 Scenario Cluster，完成规则唯一分配、可达性和数量守恒验收。
- 建立候选隔离、缓存复用、局部更新、全目录验证和人工发布审核的增量流程。
- 使用 8 条独立新错解完成增量实测，提取 9 条候选，形成 16 条新正式规则；原有 Rule ID 保持不变。

### 2. 语义检索与检查链路

- 完成 `BackgroundAnalysis + Domain → Topic → Scenario Cluster → Rule` 语义导航并接入主流程。
- Domain、Topic 和 Cluster 阶段只使用题目背景，Rule 阶段才读取待检查答案；参考答案不输入 verifier。
- 修复语义导航的结构化输出与有界恢复问题，不再将 semantic/parse failure 静默计为正常空结果。

### 3. 测评流程

- 建立 development、validation、final test 三层数据隔离原则。
- 使用 Gemini 3 Flash 构造并审计 GT，使用 Qwen30B 作为 verifier 和 direct baseline。
- 完成独立 20+20 validation：20 道错题含 60 个可定位 GT 错误，20 道正确题经 Gemini 筛选并审计。
- 固化 catalog 路径、SHA-256、输出 trace、coverage 和失败统计口径。

## 三、主要实验结果

### 1. 1123 规则链与 Qwen30B direct baseline

共同有效 38 题上：

| 系统 | Recall | Precision | 题目级 F1 | 错误定位 F1 |
|---|---:|---:|---:|---:|
| Qwen30B direct baseline | 94.7% | 64.3% | 76.6% | 38.1% |
| 1123 规则链 | 100.0% | 54.3% | 70.4% | 43.6% |

规则链提高了错误定位 Recall 和 F1，但 19 道正确题中误报 16 道，且顺序运行约比 direct baseline 慢 6.5 倍。

### 2. 1123 与 4875 完整 catalog 配置消融

共同有效 38 题上，4875 配置的题目级 F1 从 72.7% 降至 63.8%，错误定位 F1 从 43.8% 降至 24.5%。4875 配置减少了 3 个正确题 FP，但新增 5 个错题 FN，整体不优于 1123 配置。

该比较同时改变了规则集和 runtime metadata，因此不作为纯 metadata 因果结论。

### 3. 1123 规则集 metadata-only 受控消融

保持规则、Cluster、模型、Prompt 和参数不变，只回填 runtime metadata。受控组完成 40/40 有效输出，共同有效 39 题上：

| 系统 | TP | FP | TN | FN | 题目级 F1 | 错误定位 F1 |
|---|---:|---:|---:|---:|---:|---:|
| 原始 1123 | 20 | 16 | 3 | 0 | 71.4% | 43.8% |
| 1123 + runtime metadata | 9 | 8 | 11 | 11 | 48.6% | 20.3% |

metadata 使正确题 FP 从 16 降至 8，但同时使 TP 从 20 降至 9。结论是当前 metadata 方案过度抑制，不可直接采用。

## 四、正确题误报根因

1. 原始组 22 条 FP 诊断在 Rule 发布门没有可核验的前置条件、违规特征或证据要求，说明缺少有效适用性门控。
2. metadata 组剩余 17 条 FP 虽通过了下游关键词/符号重合检查，但 Rule 发布门仍没有题目侧前提与答案侧违规的显式证据；弱重合不能证明物理违规。
3. 至少 3 条剩余诊断在解释中承认被引用推导正确，随后仍发布错误，说明 Checker 存在自相矛盾和臆造违规问题。
4. metadata 导致的 11 个错题漏检全部发生在 Rule 阶段：4 题未检索到规则，7 题已检索规则但未发布诊断。

因此根因不是单一错误规则或 Topic，而是“规则适用性证据不足”与“Checker 缺少发布前一致性校验”的系统性问题。

## 五、当前决策

- 保留 1123 规则库作为高召回主线，不转向 4875 配置。
- 不直接采用当前 runtime metadata 硬性拒绝方案。
- metadata 后续只作为排序和证据特征，不单独决定是否发布诊断。
- 不依据 validation 样本编写题型、Rule ID 或样本特判，所有补强只在 development/合成数据上开发。

## 六、下一阶段计划

1. 实现通用发布门控：只有同时证明“规则前置成立”和“具体违规存在”时才发布诊断。
2. 增加通用自一致性检查，抑制“解释承认正确但仍报错”的诊断。
3. 在 development 和合成正/反例上验证 FP 下降且错题召回不显著下降。
4. 固化代码、Prompt、Catalog、模型参数和 Git commit，再抽取全新 final test。
5. final test 使用服务器和 `tmux` 运行，完整保留配置指纹、trace、coverage、失败与耗时统计。

## 七、需同步事项

- 与学长确认 upstream 中 catalog 的正式身份、版本和指纹记录方式。
- 确认 final test 数据抽样、封存和一次性运行规则。
- 统一输出 trace、coverage、semantic/parse failure 和耗时的对外汇报口径。

## 八、阶段性结论

截至本快照，已完成“规则库结构可用、链路可运行、本地原始产物可复算”的基础建设，并通过独立 validation 定位到 precision 层是当前主要瓶颈。仓库级复现清单、源码状态和非 Git 产物同步方式仍待收口；下一阶段的目标不是继续扩大规则数量，而是在不破坏召回的前提下降低正确题误报，然后进入全新 final test。
