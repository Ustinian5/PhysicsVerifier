# 效果测评

## 目的与边界

效果测评回答三个问题：

1. verifier 能否识别含物理错误的解答；
2. 诊断能否定位到与 GT 相同的答案区域；
3. unified_rules 相对同模型直接检查是否带来净收益。

测评不承担规则生成。任何被查看并用于修改代码、prompt、规则或阈值的样本都会转为开发集或验证集，不能继续作为最终测试集。

参考答案只提供给 Gemini，用于构造错误 GT 和审计正确样本；Qwen verifier 与无规则基线均不读取参考答案。

## Catalog 口径

仓库中有两个不能混用的 catalog：

| Catalog | 规模 | 当前角色 |
|---|---:|---|
| `catalogs/rules_unified_3000.json` | 1123 条规则、189 个 Scenario Cluster | 当前 development 高召回基线，本轮 5+5 和 20+20 评测对象 |
| `catalogs/rules_unified_3000_runtime_backfilled.json` | 4875 条规则、488 个 Scenario Cluster | 历史运行时参考库；完整配置消融已否决 |

两者不是同一规则集的纯 metadata 变体。每次实验必须在 `run_config.json` 中保存 catalog 路径、大小和 SHA-256，结果只能归因于实际运行的文件。

## 数据划分与防过拟合

正式采用三层数据：

| 划分 | 用途 | 是否允许据此修改系统 |
|---|---|---|
| Development | 调试流程、构造合成回归测试 | 允许 |
| Validation | 选择整体方案、门控和阈值 | 允许，但结果不再视为最终测试 |
| Final test | 冻结系统后的最终报告 | 不允许；若据此修改，必须废弃并重抽 |

约束：

- 按归一化题目文本去重，不只按样本 ID 去重。
- 历史评测集、开发集、验证集和规则构造数据必须进入排除列表。
- `extract_holdout_eval_samples.py --exclude` 会在默认排除集上累加，不会替换默认项。
- 正确样本必须经 Gemini 独立审计；`source_reward_acc=True` 不能直接当作正确标签。
- 不允许把样本 ID、特定题型、目标公式或逐题阈值写入运行时代码。
- 修复应表达一般不变量，并使用合成或最小单元测试验证。
- 标签在 Qwen 运行前冻结，不根据 verifier 输出删除或替换不利样本。
- 现有 5+5、20+20 及其消融样本均已被查看，只保留为历史结果与回归记录；不得用于 P2 开发、模式选择或阈值调整，也不能再承担 final-test 泛化结论。

## 指标口径

### 题目级

`diagnostics` 非空视为预测存在物理错误：

- TP：错题且产生诊断；
- FP：正确题但产生诊断；
- TN：正确题且无诊断；
- FN：错题但无诊断。

报告 Recall、Precision、F1、Specificity 和 Accuracy。

### 错误定位级

GT 与诊断按答案中的字符区间或段落区域匹配。模型提供的字符偏移必须先和 `evidence.quote` 验证；不一致时由 quote 在原答案中重新定位。

该指标衡量“是否指向同一答案区域”，不等价于独立的语义等价判断。

### 可靠性

API、结构化输出、语义导航或 Checker 传输/解析/schema 失败是 abstention/error，不得按空诊断计为 TN 或 FN。结果缺失也必须单列。必须同时报告：

- 有效输出数和 coverage；
- `semantic_retrieval_failure`、`checker_failure` 和 `missing_result` 数；
- 全集指标或共同有效子集指标；
- 比较多个系统臂时，使用所有臂的共同有效样本做配对指标，同时保留各臂全量 coverage 和 failure-by-stage。

## P2 Checker 协议与冻结 retrieval 回放

### 三种 Checker 模式

| 模式 | 定义 |
|---|---|
| `legacy` | 保留历史 Checker 输出和发布路径，用于兼容与对照 |
| `dual_evidence` | 要求题目侧适用性证据和解答侧违规证据均为真、置信度均不低于 `0.8`，且通过 source/span 校验 |
| `dual_evidence_consistency` | 在 `dual_evidence` 上再要求自一致性状态为 `confirmed_violation` 且置信度不低于 `0.8`；`self_corrected`、`equivalent_or_alternative` 和 `uncertain` 均拒绝发布 |

`0.8` 在 P2 效果测试前固定，对齐历史 Prompt 中的 80% 保守发布要求。它不是通过历史 5+5、20+20、消融样本或未来 validation 样本搜索得到的阈值，当前 P2 三臂不对其调参。

双证据 schema 强制来源隔离：`applicability` 只能引用 `question/context`，`violation` 只能引用 `prediction`。每段证据的模型偏移必须与对应原文切片严格相等；若不相等，仅在 quote 有且仅有一处精确匹配时修复 span。无匹配或多重匹配失败关闭，不做模糊证据补齐。

Checker 调用的传输、JSON 解析或 schema 失败会保存状态和失败数，并在两个 evaluator 中记为 `checker_failure`。这些题降低 coverage，不进入 TN/FN，也不进入错误级 Recall 分母。非 `legacy` 模式下，bottom-up experience-code fail 只进入 symbolic audit，不进入主诊断，evaluator 也不会把它当作模型预测。

### 受控回放流程

`scripts/run_checker_replay.py` 不执行 retrieval 或 bottom-up 检查。它从已冻结的语义 retrieval trace 重建本次可执行 Rule，并校验 dataset、trace、catalog、有序 ID、Rule 归属和 SHA-256。所有命令必须在 conda `physicsverifier` 环境执行。

第一步只生成冻结 manifest（以下路径为命名模板）：

```bash
conda run -n physicsverifier python scripts/run_checker_replay.py \
  --dataset data/p2_development.json \
  --frozen-retrieval results/p2/frozen_retrieval.json \
  --catalog catalogs/rules_unified_3000.json \
  --frozen-manifest experiments/manifests/p2-checker-replay.json \
  --prepare-manifest-only
```

第二步每次只运行一个模式，并为每个模式使用独立 output、report 和 LLM trace：

```bash
conda run -n physicsverifier python scripts/run_checker_replay.py \
  --dataset data/p2_development.json \
  --frozen-retrieval results/p2/frozen_retrieval.json \
  --catalog catalogs/rules_unified_3000.json \
  --frozen-manifest experiments/manifests/p2-checker-replay.json \
  --mode dual_evidence \
  --model qwen3-30b-a3b-instruct-2507 \
  --checker-json-attempts 3 \
  --run-kind development \
  --checkpoint-every 1 \
  --output results/p2/dual_evidence.json \
  --report results/p2/dual_evidence.report.json \
  --llm-trace results/p2/dual_evidence.llm_trace.jsonl
```

`legacy`、`dual_evidence` 和 `dual_evidence_consistency` 要分别独立运行，不得共用 output（同时作为原子 checkpoint）、report 或 LLM trace。三臂共享冻结 retrieval，但 Checker prompt/schema、Checker 候选诊断与 release gate 会随模式改变，因此它们是三个独立的 **Checker + release gate system arms**，不是共享 candidates 的 gate-only 消融。

回放配置绑定 frozen manifest、Git/source tree、conda Python/package set、API endpoint 摘要和传输参数。`--run-kind validation`/`final` 强制 clean worktree 且禁止 Checker cache，运行结束再次核验 source tree 未变化。raw-response trace 不保存 prompt；`--resume` 校验 sidecar 与 trace 前缀，并审计崩溃后已写入但尚未 checkpoint 的 orphan trace。

第三步在三臂全部终态后冻结共同有效配对集：

```bash
conda run -n physicsverifier python scripts/build_checker_common_valid.py \
  --dataset data/p2_development.json \
  --arm legacy results/p2/legacy.json results/p2/legacy.report.json \
  --arm dual_evidence results/p2/dual_evidence.json results/p2/dual_evidence.report.json \
  --arm dual_evidence_consistency results/p2/dual_evidence_consistency.json results/p2/dual_evidence_consistency.report.json \
  --output-dataset results/p2/common_valid.json \
  --manifest experiments/manifests/p2-common-valid.json
```

该工具要求三臂禁用 Checker cache；除 `system_arm` 和臂本地产物路径外，完整配置必须一致。它严格校验 typed ID、输入哈希、source/runtime/API 身份、report/result 绑定及逐题终态，并实际读取三份不同的 LLM trace，核验 SHA/size/record/raw-response/parse-status，拒绝缺失、篡改、共享路径和 prompt 字段。输出 dataset 与 manifest 均不可覆盖。三个系统臂分别用现有 evaluator 在 `common_valid.json` 上计算配对指标；同时报告原始三臂 report 的全量 coverage/failure_counts，以及 common-valid manifest 中各臂的 failure_by_stage。

当前状态是：**P2 工程收口已完成，尚无效果结论**。既有两题 Qwen30B smoke 中，明确矛盾发布 1 条诊断，已自我修正陈述返回合法空结果且发布 0 条诊断，均无 Checker failure。smoke 只证明真实端点能产出严格结果，并在该合成样例上抑制发布，不证明任一模式改善 Precision、Recall 或 F1。合并 P3 后全量回归为 365/365 通过。

## P3 规则级条件 Checker 门禁

### 两个 estimand 严格分离

| 实验 | 候选来源 | 回答的问题 | 是否参与候选判门 |
|---|---|---|---|
| Primary controlled gate | `frozen_target_binding` | 目标规则已提供时，Checker + release gate 是否正确发布/抑制 | 是 |
| Secondary trace schema audit | `run_verifier.py --retrieval-only` 兼容 semantic trace | trace 中目标规则的命中、抑制与失败分类 | 否 |

Primary 使用每例唯一目标规则及 `fixed_control_0_1=1.0`。该分数是控制绑定常量，不是 semantic 相似度、模型置信度或“完美检索”观测值。因此主实验结论只能写成**条件 Checker + release gate 性能**，不能写成 retrieval 改善、端到端 verifier 改善或统一规则链总体效果。Secondary 当前只做 trace schema 与分类审计，不与 Primary 合并计算 Recall、FPR 或 acceptance；在增加运行 sidecar 前也不能称为 production 外部效度。

### Gemini GT 与不可变 generation manifest

每条规则的成功响应由 `gemini-3-flash-preview` 同时构造以下 5 种机制，总计严格为 300 例：

1. `true_violation`：适用、当前确有违规、应发布、`confirmed_violation`；
2. `applicable_correct`：适用但解答正确，不发布；
3. `symbol_overlap_inapplicable`：只有表面符号重合，规则不适用，不发布；
4. `equivalent_alternative`：等价公式或替代解法，不发布、`equivalent_or_alternative`；
5. `insufficient_or_self_corrected`：30 条规则构造 `self_corrected`，30 条构造 `insufficient_information`，均不发布。

生成响应必须是 exact JSON object，key、顺序机制和 expected 映射固定；applicability 证据只能来自 `question/context`，violation、被取代陈述和修正证据只能来自 `prediction`。quote 必须唯一出现并与 0-based half-open span 对齐；只允许按唯一 quote 修正偏移。schema、语义标签或证据不合格时按冻结尝试策略重试，不能删除困难样本或换规则。

generation manifest 绑定 catalog、固定规则计划、模型、Prompt 版本、源码状态、conda/package set、API endpoint 摘要、dataset、target-binding trace、原始响应 trace、checkpoint、顺序 ID、大小和 SHA-256。完整 60 规则生成只允许 `validation/final`、clean worktree、真实 API provider；产物和 manifest 不可静默覆盖。

### 三臂三重复与门槛

正式设计为 60 规则 × 5 机制 × 3 arms × 3 independent repetitions，共 2700 个 Checker 运行单元。三个 arm 为：

- `legacy`：消融 baseline；
- `dual_evidence`：消融 baseline；
- `dual_evidence_consistency`：唯一 candidate arm。

每格独立调用 Qwen30B，关闭 cache，并使用独立 output、report、LLM raw-response trace；正式配置固定 `checker_json_attempts=3`、`llm_temperature=0.1`、`llm_max_output_tokens=2048`、`precision_mode=strict`。dataset 中的 GT、expected 和 target metadata 不作为题目字段输入 Checker；目标规则只通过预注册冻结候选进入 SRD，GT 只用于评估。

评估器构造三个不可互换的共同有效集合：

- `C[r]`：第 `r` 次重复内三个 arm 的共同有效样本，用于臂间配对；
- `T[a]`：同一 arm 三次重复的共同有效样本，用于发布稳定性；
- `G`：全部九格的全局共同有效样本，用于全局审计。

传输、API、解析、schema、缺失结果、target 缺失/重复或 trace/manifest 不一致均为 coverage failure，不是 TN/FN，也不进入负类“预测正确”计数。

只有 `dual_evidence_consistency` 判门，而且每次重复必须分别满足全部条件：

- 结构化输出率 ≥ 99%；
- `true_violation` Recall ≥ 90%；
- `applicable_correct`、`symbol_overlap_inapplicable`、`equivalent_alternative`、`insufficient_or_self_corrected` 四类 FPR **各自** ≤ 5%；
- self-corrected probe 发布诊断数 = 0；
- 可评估的 protocol contradiction 数 = 0；
- 三次发布决策一致率 ≥ 95%。

不允许对三次取平均后过线，也不允许合并四类负样本稀释某一类误报。两个 baseline 只提供受控消融对照，不承担 acceptance 门槛。

### Metadata-only 受控组

为隔离 metadata 作用，另行基于 1123 条库构造了受控 catalog：

- 规则数仍为 1123、Topic-with-rules 为 76、Cluster 为 189；
- Rule ID、标题、触发条件、检查逻辑、symbolic hint 和 Cluster 归属的投影哈希完全相同；
- 只补齐 topic routing、match features、preconditions、negative conditions、evidence requirements 等 runtime metadata；
- 构造过程不读取 validation 样本，也不调用模型。

服务恢复后通过 3/3 稳定性门禁，剩余样本以最多 3 题的可持久化小批次续跑，最终得到 40/40 有效输出。小批次只改变执行调度，模型、prompt、catalog 和参数不变。原始组有 1 题无效，因此配对共同有效集为 39 题：20 错、19 对。

| 系统 | TP | FP | TN | FN | Recall | Precision | F1 | Specificity | Accuracy |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 原始 1123 | 20 | 16 | 3 | 0 | 100.0% | 55.6% | 71.4% | 15.8% | 59.0% |
| 1123 + runtime metadata | 9 | 8 | 11 | 11 | 45.0% | 52.9% | 48.6% | 57.9% | 51.3% |

配对结果为两者都正确 11 题、都错误 7 题、原始组独占正确 12 题、metadata 组独占正确 9 题，精确双侧 `p=0.664`。在 20 道错题、60 个 GT 错误上，错误定位 F1 从 43.8% 降至 20.3%。

正确题 FP 由 16/19 降至 8/19：9 题被修复、7 题持续误报、1 题新增误报，配对 `p=0.0215`。但 metadata 同时使 11/20 错题从命中变为漏检；其中 4 题在 Rule 阶段没有检索到规则，7 题检索到 1–2 条规则但未发布诊断。

误报根因为两层：原始组 22 条 FP 诊断在 semantic publish gate 没有可核验的前提、违规特征或证据要求，metadata 组剩余 17 条 FP 虽有 grounding，且都通过了下游 quote/关键词/符号重合检查，但 semantic gate 的题目侧前提与答案侧违规证据仍为空。通用符号重合只能证明表面相关，不能证明物理违规；至少 3 条解释还明确承认被引推导正确后仍发布错误。因此剩余 FP 的主因是 Checker 在弱相关证据上臆造违规并缺少自一致性门，而非单纯 Topic 导航错误。

metadata 回填也不是人工核验的物理谓词：1123 条中 524 条复用参考字段，599 条从规则文本机械生成；609 条 generalized 规则的 runtime `support.count` 均为 0，所有规则默认 `publishable=true`。这些字段会扩张 SRD 并改变 Checker 行为，足以淘汰该配置，但不能把单次运行差值精确解释为高质量 metadata 的纯因果效应。

## 当前结论

- 1123 配置仍保留较强的错误召回和定位信号，但 FP 高；
- 4875 完整配置降低部分 FP，却显著损失错误召回与定位质量；
- 两套规则配置的题目级效果和运行成本都不优于 direct baseline；
- metadata-only 受控组证明当前回填方案会降低 FP，但导致更严重的错题漏检，不可直接采用；
- 三套现有完整配置都不应直接扩大为服务器 final-test 实验。

P2 通用 precision 层已收口；P3 已把固定 60 规则计划、Gemini 五机制 GT、honest target-binding 主门禁、三臂三重复评估和 semantic trace schema 审计实现为独立入口。下一步是在 clean commit 上生成正式 300 例，再运行九格 Qwen30B 回放；secondary retrieval 需先增加执行 sidecar。结果出来前不声称任何模式改善。历史 5+5、20+20 及消融样本不参与 P2/P3 开发、选择或调参。预注册门槛见[项目进展](项目进展.md)。

## 复现状态

当前应表述为“本地原始产物完整、可复算，仓库级复现尚未闭环”：

- 原始 20+20 `run_config.json` 记录了模型、seed、参数和 catalog SHA，但未记录 Git commit 与 dirty 状态；
- 4875 消融记录了 `git_head=523071b…`、dirty 状态和关键源码 SHA；metadata-only 记录了数据、catalog 与输出 SHA，但没有完整源码状态；
- `data/` 约 3.1 GB、`results/` 约 693 MB，均被 Git 忽略，不能依赖 GitHub 自动同步到服务器；
- 后续冻结实验必须使用受版本控制的 manifest，并以 `rsync`、对象存储或等价通道传输非 Git 产物后校验 SHA-256。
- P2/P3 回放 manifest 可冻结 dataset、semantic 或 target-binding trace、catalog、有序 ID 和 selection projection；每臂 report 进一步绑定 source tree、conda runtime/package set、API endpoint、传输参数和 frozen-manifest SHA。P3 generation manifest 另绑定 Gemini 原始响应与 GT 产物。正式 P3 样本和 Qwen 回放尚未运行，因此没有新效果指标可报告。

## 本地与服务器运行

本地小规模：

```bash
conda run -n physicsverifier python -m unittest discover -s tests -p 'test_*.py'
```

服务器大规模运行前：

1. 在实验室 GitHub 同步目录确认 commit：`git rev-parse HEAD`；
2. 检查工作区和数据文件：`git status --short`；
3. 所有 Python 命令显式使用 `conda run -n physicsverifier`；
4. 使用 tmux，并把 stdout/stderr 保存到实验目录；
5. 在运行记录中写入 commit、catalog SHA-256、模型、seed、命令和开始时间。

```bash
tmux new -s physicsverifier_eval
conda run -n physicsverifier python scripts/run_verifier.py ... 2>&1 | tee results/eval_run/verifier.log

# Ctrl-b d 离开
tmux attach -t physicsverifier_eval
```

服务器只用于冻结配置的大规模运行，不在服务器结果出来后直接覆盖本地规则库或修改 final-test 标签。
