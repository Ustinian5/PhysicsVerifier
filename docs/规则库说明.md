# 规则库说明

## 运行结构

统一规则库按以下层级组织：

```text
Domain → Topic → Scenario Cluster → Rule Group → Rule
```

`Rule Group` 是可选内部层。Domain、Topic 和 Cluster 导航只读取题目背景；Rule 层才读取待检查答案。运行时以命中的 Scenario Cluster 为检索边界，不在命中后重新扫描整个 Topic。

1123 与 4875 不是同一规则集的纯 metadata 变体。命令行没有统一库的隐式默认值；任何实验都必须显式指定 catalog 并记录完整 SHA-256。

## 构建来源与正式流程

主要文件：

| 文件 | 作用 |
|---|---|
| `catalogs/rules_catalog_top_down.json` | 物理知识骨架 |
| `catalogs/rules_300_tagged.json` | 300 样本标注规则输入 |
| `catalogs/semantic_experience_distilled_300.json` | 300 样本蒸馏规则输入 |
| `catalogs/scenario_cluster_blueprints.json` | Scenario Cluster 配置源 |
| `catalogs/rules_unified.json` | 514 条基线规则 |
| `scripts/unified_rules_pipeline.py` | 规则构建主入口 |
| `scripts/validate_unified_catalog_structure.py` | 全量结构验证 |

正式构建链为：

```text
单题候选 → Topic 内聚类 → 多样本概括 → 正式规则聚类
→ 目录重建 → 全量结构验证 → 人工发布审核
```

硬约束：

- 新生成规则必须由多样本支持；514 条历史基线规则作为单样本 legacy 豁免保留，并单独标记证据等级，不将豁免扩展到新规则；
- 残余项、失败批次和缓存必须保留，不能静默丢失；
- Rule ID 必须唯一、引用合法，并在树中恰好可达一次；
- 运行库是构建产物，不直接手改；新增与修正进入构建输入；
- 新增流程必须比较 Rule 内容、来源和 Rule→Cluster→Rule Group 映射，不能只比较 Topic 内 Rule-ID 集合。

## 1123 development 基线审计

### 规模与覆盖

- 规则来源：609 条 generalized + 514 条 baseline = 1123 条；
- 6 个 Domain、123 个 Topic，其中 76 个 Topic 含规则；
- 189 个 Scenario Cluster；存在 3 个空 Cluster，均位于没有规则的 `Optics / Laser Principles and Applications`；
- Domain 规则数：Mechanics 461、Electromagnetism 299、Thermodynamics 173、Modern Physics 125、Optics 57、Experimental Physics 8；
- Topic 规则数中位数 9、P90 31、最大 78；
- Cluster 规则数中位数 5、P90 12、最大 29；18 个单规则 Cluster，13 个 Cluster 超过 12 条。

构建报告中的“残余桶最大 12”只描述 102 个 residual bucket；它与全目录 Cluster 最大 29 不矛盾，但不能被表述为所有 Cluster 都不超过 12。

聚类覆盖也需区分“真实 embedding 聚类”和“最终被分配到某个桶”：

- embedding 主簇覆盖 343/1123，覆盖率 30.54%；
- 780 条先成为 embedding residual；最终仍有 572 条位于 102 个 `residual_rules_*` deferred bucket，占 50.9%；
- matcher 对 deferred 路径采用有界恢复，并不会扫描全部 residual bucket。因此结构上的 100% 可达，不等于每次查询都有同等的运行时被检索机会。

### 结构质量与证据边界

- 结构验证通过：1123 条规则无重复、无丢失、全部可达；
- 609 条 generalized 规则在构建审计中均由至少两个不同样本支持；2927 条未满足概括条件的候选仍保留；514 条 baseline 规则只有单样本支持，占正式库 45.8%，属于历史豁免；
- 当前精简运行 catalog 不携带 `support`、`source_rule_ids`、`preconditions`、`violation_signatures`、`negative_conditions`、`evidence_requirements` 等运行证据字段；因此无法仅凭运行产物复核每条规则的经验支持；
- `rules_unified_quality_report.json` 的 94 分只基于结构检查和 6 题 smoke，其中 2 题正常为空，不是端到端效果分。

重复审计发现 2 组同标题重复；按 Topic 与 symbolic canonical 还存在 10 组、20 条潜在重复。后者只是待人工复核候选，不能直接批量删除。

低风险结构修复已完成：lexical 与 semantic runtime 只保留含有效 Rule ID 的 Topic，并过滤空 Cluster、未知引用和空 Rule Group。原始 catalog 仍保持 123 Topic / 189 Cluster；运行时候选为 76 Topic / 186 Cluster，不删除节点，也不改变任何可执行 Rule 的可达性或语义。

## 4875 历史参考库审计

- 93 个 Topic 含规则、488 个 Cluster；Topic 规则数中位数 33、最大 285，Cluster 规则数中位数 7、最大 108；
- runtime metadata 主字段覆盖完整，但 `llm_hints` 和 `source_rule_ids` 各只有约 10.5% 的规则非空；
- 2429 条规则位于主路径，2150 条位于 deferred、296 条位于 general fallback；非主路径合计 50.2%，最大 Cluster 108 条；
- 47 组同标题重复；按 symbolic canonical 有 90 组潜在重复、涉及 190 条规则，均需人工或语义复核后才能处理；
- 相对 1123，该文件同时改变规则集合、Topic 覆盖、Cluster 划分和 metadata，不能作为纯 metadata 对照；
- 20+20 配置消融中，它减少 3 个正确题 FP，却增加 5 个错题 FN，题目级与错误定位级 F1 均下降，故不晋升为当前方案。

结构字段更丰富不等于效果更好；4875 仅作历史复现和完整配置对照。

## 1139 增量候选审计

1139 候选不能发布，原因不是结构文件损坏，而是增量语义边界没有被现有验证器检查：

- 8 条新错解抽取 9 条候选，最终新增 16 条规则；只有 1 条新增规则包含任一新样本来源，其余 15 条由旧样本重新概括产生；
- generalized 集从 609 变为 605：旧输出少 20 条、新输出 16 条；preserve 策略又把旧 20 条保留进最终库，形成未充分审核的单调叠加；
- 118 条旧规则更换 Scenario Cluster，覆盖 11 个 Topic，其中 6 个不在声明的 affected topics；
- `incremental_validation.json` 只比较各 Topic 的 Rule-ID 集合，所以没有发现 Cluster 重分配，错误给出 `unexpected_changed_topics=[]`；
- 历史 manifest 的基线 SHA 与当前 1123 不一致，原始基线文件已经不存在，因此该产物同时不可复现；
- 8 条新样本检索只有 1/8 返回规则，2 题 verifier smoke 中 1 题为空，不能证明效果提升。

P1 已补齐逐阶段父产物 SHA 链、formal/precluster 确定性重放、Domain/Topic 定义、旧 Rule/Cluster/Rule Group 相对顺序、Rule→Cluster→Rule Group、Cluster 定义、unexpected Topic/Cluster、generalized 增删改、来源覆盖和预注册预算门禁。用当前 1123 基线受控重建时，16 条新增 Rule 的 3 个 Topic 均通过 exact-once 蓝图覆盖，旧规则 Cluster/Rule Group 迁移与 unexpected Topic 均为 0，但 1139 仍因超预算、generalized 漂移和来源覆盖 `1/16` 被拒绝；因此修复门禁不改变“不晋升”的结论。

## 当前误报根因

发布过程存在两层不同的“证据”：

1. Rule/semantic publish gate：当前默认最低语义分为 0，并明确不生成或验证 `precondition_hits`、`violation_signature_hits` 和 `evidence_requirement_hits`；
2. downstream release gate：主要验证答案 quote 可定位，以及规则/诊断与 quote 的关键词或符号重合。

第二层只能说明文本相关，不能证明规则适用或物理矛盾。受控实验进一步表明：

- 原始 1123 的 16 个正确题 FP 产生 22 条诊断，涉及 19 条不同规则；误报不是单一坏规则造成；
- metadata 组剩余 17 条 FP 都有 grounding 和 release-gate 关键词/符号命中，但 semantic gate 仍没有题目侧前提与答案侧违规证据；
- 通用符号重合容易放行无关诊断，至少 3 条解释甚至明确承认推导正确后仍报错；
- metadata 硬拒绝虽降低 FP，却在 Rule 阶段漏掉 11/20 错题。

现有 metadata 本身也不能视为可信物理谓词：1123+metadata 中 524 条复用参考字段，599 条从规则标题、触发条件和检查逻辑机械抽词；609 条 generalized 规则的 `support.count` 被写为 0，全部规则默认 `publishable=true`，并使用相同的 3 条 `negative_conditions`。回填后的 `path.cluster` 还统一写成 `unclustered`，与真实目录分配不一致。这解释了为什么“字段齐全”会让 SRD 更强硬，却没有产生可靠的适用性证明。

因此下一步不黑名单规则，不继续机械回填 metadata，也不针对 validation 加 Prompt 特例。正确修复是结构化双证据 gate：分别从 `question/context` 和 `prediction` 提取可定位证据，二者同时成立且解释自洽时才能发布。

## 维护与发布门禁

一个 catalog 只有同时满足以下条件才能晋升：

1. **身份完整**：路径、SHA-256、构建输入、源码 commit 和 dirty 状态已记录；
2. **结构合法**：Rule 唯一、引用合法、全部可达、无意外空 runtime 节点；
3. **增量受控**：输入与运行配置身份一致，来源覆盖、蓝图 exact-once 审计和 Rule→Cluster→Rule Group diff 符合预声明 scope；
4. **效果通过**：在独立 development 上同时满足预注册 Recall、Specificity、定位 F1 和 coverage 门槛；
5. **人工审核**：变更报告与代表性 trace 已复核；
6. **冻结复测**：冻结后才可进入全新 final test。

当前只有 1123 被允许作为 development 基线；没有 catalog 获得 final-test 发布资格。具体实验门槛见[项目进展](项目进展.md)，指标与历史结果见[效果测评](效果测评.md)。
