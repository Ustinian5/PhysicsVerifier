# 增量规则流程

## 目标

新增样本只补充现有规则库，不生成平行规则库，也不直接把单题规则写成正式规则。

## 流程

```text
新增样本
→ 抽取带来源的候选规则
→ 并入候选池
→ 仅为新增或变化候选计算 embedding
→ 在受影响 Topic 内重新聚类、概括
→ 将概括结果与现有正式规则比较
→ 更新受影响 Topic 的正式规则和规则簇
→ 重建完整目录并做结构、检索回归
```

处理原则：

- 与正式规则完全相同：不新增规则，只记录已覆盖。
- 与候选完全相同：合并 `sample_ids` 和支持数量。
- 语义相近：交给 Topic 内 embedding 聚类，不用字符串规则自动合并。
- 只有一个样本支持：继续留在候选池。
- 至少两个不同样本支持同一机制：允许概括为正式规则。
- 概括结果与已有正式规则同机制：保留原 Rule ID，只补来源和支持。
- 概括结果是新机制：新增正式规则；不确定项进入人工审核，不自动覆盖。
- 当前正式目录是增量构建的权威基线；旧 Rule ID 不得静默删除，但同机制重概括项也不得与旧规则无条件叠加。任何替换、保留或新增都必须给出来源映射和人工审核记录。
- 未受影响 Topic 的规则核心内容、Rule→Cluster→Rule Group 映射和顺序哈希必须保持不变；Rule ID 和来源关系必须保留。

## 准备入口

```bash
conda run -n physicsverifier python scripts/prepare_incremental_update.py \
  --new-candidates results/unified_rules_incremental/new_candidates.json
```

该命令不调用 API，也不修改当前正式库。它会：

- 合并候选并输出受影响 Topic。
- 建立 `results/unified_rules_incremental/` 隔离工作区。
- 在 `incremental_manifest.json` v2 中冻结 8 类外部基线输入和 3 个确定性候选准备产物的路径、大小与 SHA-256，并用 configuration SHA 固定候选变化、declared Topic、六步命令、模型参数与变更预算；事后修改任一项会直接失败。
- 以当前正式 catalog 的 Rule 顺序和 Cluster 拓扑作为 additive 权威基线；新规则只能进入新增 Cluster，不得重排或迁移旧规则。
- 复用 embedding 缓存；generalization 与 cluster-label 的缓存指纹只绑定输入内容、Prompt 版本、模型链和行为参数，产物 metadata 另行绑定本轮 configuration SHA 与直接父产物 SHA。scope、路径或预算变化不会误触发模型重算；无 v2 指纹的历史结果会执行一次安全失效。
- 生成六步 conda 运行清单；所有命令均显式使用 `physicsverifier` 环境。

按清单依次运行后，candidate embedding、generalization、formal、formal embedding input、precluster catalog、formal embedding 和 cluster-label 产物必须形成逐父文件原始 SHA-256 链。formal/precluster 还会在 finalize 前做一次确定性重放，确保新增 Rule 内容确实由已绑定 generalized 与冻结基线生成。generalization 必须完整且失败批次、缺失候选均为 0；cluster-label 必须覆盖全部目标 Topic，且每个 proposal 都必须来自模型成功输出。网络/API 中断时生成的 `embedding_fallback` 只用于保存进度，会被 finalize 硬拒绝；重跑同一 resume 命令会自动重试这些 Topic。`finalize_incremental_update.py` 在构建前重算 candidate delta、复核整条产物链与 proposal 内容指纹，再生成候选目录和审核报告。任一不匹配都会硬失败并留下失败报告。

默认 `additive` 预算由本轮新增/变化 candidate 数量导出。确需改变旧规则 Cluster、Rule Group 或 Cluster 定义时，必须在 prepare 前改用 `--change-mode scoped_recluster`，同时通过 `--allow-recluster-topic DOMAIN::TOPIC` 和对应 `--max-*` 参数预声明范围。声明 Topic 采用完整 generated blueprint 替换旧拓扑，且构建前必须对该 Topic 的全部正式 Rule 做 exact-once 覆盖校验；缺失、重复、跨 Topic、空 ID 均直接失败。未声明 Topic 仍按 additive 冻结。不得在看到输出或效果样本后补调范围与预算。

最终产物不会自动覆盖 `catalogs/rules_unified_3000.json`。只有结构验证、变化范围审核和独立检索回归全部通过后，才人工替换正式目录。

`incremental_validation.json` 分别记录 `manifest_validation`、`candidate_delta_validation`、`output_binding_validation`、`artifact_bundle_validation`、`topology_validation`、`generalized_diff`、`lineage`、`catalog_diff` 和 `change_policy`，并给出最终 catalog/blueprint SHA-256；任何失败项都不能被总分或人工备注抵消。

验证阶段可直接接入主流程：

```bash
conda run -n physicsverifier python scripts/run_verifier.py \
  --input data/test.json \
  --output results/test.json \
  --unified-catalog results/unified_rules_incremental/rules_unified_incremental.json \
  --unified-retrieval-mode semantic
```

## 验收

- 新候选、重复候选、正式规则已覆盖项数量守恒。
- Domain/Topic 导航定义不得漂移；Domain/Topic 的旧节点相对顺序以及 Topic 内旧 Rule 相对顺序全模式冻结，旧 Cluster、Cluster 内 Rule、Rule Group 及组内 Rule 的相对顺序只允许在预声明 scoped Topic 内变化。
- 未受影响 Topic 的规则核心、Rule→Cluster→Rule Group 映射、Cluster 定义和顺序哈希不变化。
- 新增 Rule 的 additive 蓝图和 scoped Topic 的全量蓝图都必须在构建前通过 Topic 内 exact-once Rule 覆盖审计。
- 最终目录无重复 Rule ID、无失联规则、无非法引用。
- 每条新增正式规则必须至少包含一个新增或发生变化的候选来源；新增 Rule ID 必须进入 `incremental_validation.json` 人工审核。
- generalized 输出相对冻结基线的新增、删除和内容修改必须分别进入预算，不能由 preserve 策略掩盖。
- 旧 Rule ID 删除、同机制新旧规则叠加、超出 affected scope 的 Topic/Cluster 变化和超过预注册变更预算都会阻断接入。
- 本地独立样本检索无结构错误后，才上服务器跑较大实验。

- 262 个概括批次只重算 10 个，API 成功 10/10。
- 候选目录由 1123 条旧规则和 16 条新增规则组成，旧 Rule ID 删除数为 0。
- 最终目录结构校验通过；4370 个候选全部被计入，1139 条正式规则均恰好可达一次。
- 新目录对 8 条样本完成语义检索：8/8 跑完、结构错误 0；1 条返回规则，7 条正常返回空结果。
- 完整 verifier 回归 2/2 跑完：1 条进入 Semantic Checker 并产生诊断，1 条正常空结果；新增 Rule ID 已进入真实导航候选。
- 质量报告给出 97 和 `usable_with_known_gaps`，但只包含结构检查与 2 题 smoke，不是效果分。

2026-08-06 的深入审计发现原验收结论存在漏检：

- 16 条新增规则中只有 1 条包含任一新样本来源，其余 15 条由旧候选重新概括产生；
- generalized 输出从 609 变为 605：20 条旧输出消失、16 条新输出出现；preserve 策略又保留旧 20 条，形成未审核的单调叠加；
- 118 条旧规则更换 Scenario Cluster，涉及 11 个 Topic，其中 6 个不在声明的 affected topics；
- 旧 validator 只比较 Topic 内 Rule-ID 集合，没有比较 Rule→Cluster 分配，因此错误报告 `unexpected_changed_topics=[]`。

历史 manifest 还记录了已不存在的基线 SHA `0a299a…`，而当前 1123 基线为 `838506…`，所以原候选不可复现。P1 门禁现已实现；用当前基线做受控 additive 回放后，16 条新增 Rule 的 3 个受影响 Topic 均通过 exact-once 蓝图覆盖，旧规则 Cluster/Rule Group 迁移均为 0、unexpected Topic 为 0，但 1139 仍因新增规则超预算、generalized `+16/-20/修改12` 和本轮来源覆盖仅 `1/16` 被拒绝。它不能替换 1123 development 基线，也不能靠事后放宽预算晋升。
