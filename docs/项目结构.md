# 项目结构

## 目录职责

```text
PhysicsVerifier/
├── core/             verifier 主流程、语义导航、规则检索与 Checker 协议
├── rules/            规则插件接口和确定性基础检查
├── rule_framework/   catalog 构建、规范化、维护与验证
├── symbolic/         可选符号核查运行时及生成代码
├── scripts/          当前命令行入口和构建/评测工具
│   └── legacy/       旧实验包装器和专用分析程序
├── catalogs/         正式 catalog、构建输入与 legacy 版本
├── tests/            单元测试、回归测试及小型 fixtures
├── docs/             共享设计、进展与实验结论文档
├── experiments/      Git 跟踪的冻结实验 manifest 与说明
├── data/             本地数据集，Git 忽略
├── results/          本地/服务器运行产物，Git 忽略
└── private_docs/     个人服务器和协作记录，Git 忽略
```

## 正式入口

| 工作 | 入口 |
|---|---|
| 运行 verifier | `scripts/run_verifier.py` |
| 完整效果测评 | `scripts/run_physics_eval_pipeline.py` |
| P3 固定抽样与五机制 GT | `scripts/build_checker_mechanism_dataset.py` |
| 冻结 retrieval 的 Checker 回放 | `scripts/run_checker_replay.py` |
| 冻结三臂共同有效集 | `scripts/build_checker_common_valid.py` |
| P3 条件 Checker 门禁 | `scripts/evaluate_checker_mechanism_gate.py` |
| P3 semantic retrieval trace schema 审计 | `scripts/audit_checker_mechanism_semantic_retrieval.py` |
| 同模型直接基线 | `scripts/run_llm_checker_baseline.py` |
| unified_rules 构建 | `scripts/unified_rules_pipeline.py` |
| 增量准备 / 严格收口 | `scripts/prepare_incremental_update.py` / `scripts/finalize_incremental_update.py` |
| 增量纯逻辑审计 | `rule_framework/incremental_validation.py` |
| 全量测试 | `conda run -n physicsverifier python -m unittest discover -s tests -p 'test_*.py'` |

更细的脚本职责见 [`scripts/README.md`](../scripts/README.md)。

本机 Python 入口统一在 conda `physicsverifier` 环境运行，不直接调用系统 Python。个人计算资源的环境与命令不进入共享文档。

## P2 Checker 运行边界

- `core/semantic_rule_checker.py` 定义 `legacy`、`dual_evidence` 和 `dual_evidence_consistency` 三种协议。双证据模式隔离 `question/context` 适用性证据与 `prediction` 违规证据，并对原文切片做严格 span 校验；consistency 模式再拒绝自我修正、等价/替代解法和不确定结论。
- Checker 最低置信度固定为 `0.8`，是 P2 效果测试前固定的通用协议值，不是基于历史或未来测试样本调参。
- `core/physics_rule_verifier.py` 负责将 Checker 证据门与 release gate 连接到主流程。非 `legacy` 时，bottom-up experience-code 仅写入审计产物，不发布为主诊断。
- `scripts/run_verifier.py` 与 `scripts/run_physics_eval_pipeline.py` 透传 Checker 模式/尝试次数，并保存 `checker_status` 和 failure count。两个 evaluator 将 Checker、semantic 和 missing-result 失败单列到 coverage，不将失败样本当作 TN/FN；非 `legacy` 的 bottom-up audit fail 也不计为预测。
- `scripts/run_checker_replay.py` 先用 `--prepare-manifest-only` 冻结 dataset、semantic retrieval trace 或显式 target-binding trace、catalog、有序 ID 和 SHA-256，再每次运行一个模式。三份运行是独立的 **Checker + release gate system arms**：共享冻结候选输入，不共享 Checker 响应和诊断。
- 回放 report 绑定 frozen manifest、Git/source tree、conda runtime/package set、API endpoint 和传输参数；每个非 transport 响应还绑定供应商 `actual_model` 与非空、格内唯一的 `response_id`，并要求实际模型精确匹配配置。validation/final 强制 clean worktree 且禁止 Checker cache。raw-response trace 不保存 prompt，resume 会校验 trace 前缀并审计 orphan trace。
- `scripts/build_checker_common_valid.py` 要求三臂除臂标识/本地产物路径外配置一致，校验 typed ID、输入与运行身份、report/result、实际 LLM trace 和逐题终态，冻结均不可覆盖的共同有效数据集及 manifest。配对指标使用该子集，同时报告原始 report 的全量 coverage/failure_counts 和共同有效 manifest 的 failure_by_stage。
- 历史 5+5、20+20 及其消融样本不用于 P2/P3 开发、选择或阈值调整。P2 工程已收口；当前 P3 正式 300 例与 Qwen30B 九格回放尚未运行，因此没有效果结论。合并 P3 与响应身份门禁后全量回归为 368/368 通过。

## P3 工程边界

- `scripts/build_checker_mechanism_dataset.py` 只从 SHA-256 固定的 1123 条 catalog 构造 60 规则计划，不读取 `data/` 中的历史测评集或 `results/` 中的既有输出。计划按 6 个 Domain、`gen`/`exp`、symbolic primitive 与 `trigger_scope_proxy` 精确配额抽样，任一分层不足即失败关闭。
- `trigger_scope_proxy` 是 trigger 经 NFC/空白规范化后，在 `Domain × origin` 内按 Unicode 字符长度二分得到的词法 proxy。`broad_proxy`/`narrow_proxy` 只是操作标签，不代表语义覆盖范围。
- Gemini 3 Flash 对每条目标规则构造 5 个机制样本。严格校验 exact schema、固定 GT 映射、证据 source/span、唯一 quote、字符区间与跨样本去重；generation manifest 绑定计划、catalog、模型/Prompt、源码/runtime/API 和全部产物指纹。
- 主实验候选输入是 `candidate_source=frozen_target_binding`：每个样本只提供预注册目标规则，固定 `1.0` 分值仅标识控制绑定。该路径估计“目标规则已给定时的 Checker + release gate 性能”，明确不估计 retrieval 或端到端 verifier 效果。
- 主矩阵为三臂 × 三次独立重复。只有 `dual_evidence_consistency` 参与 acceptance；`legacy`、`dual_evidence` 是消融基线。评估器分别形成重复内三臂共同有效集 `C[r]`、臂内三重复共同有效集 `T[a]` 和九格全局共同有效集 `G`；所有执行失败只降低 coverage。
- `scripts/audit_checker_mechanism_semantic_retrieval.py` 单独审计 `run_verifier.py --retrieval-only` 兼容 trace 的目标可执行命中、publish gate 抑制、仅错误规则、空结果、retrieval failure、排名和候选数。当前缺少绑定源码/runtime/model/API/参数/output 的执行 sidecar，因此它只证明 schema 与分类兼容，不证明 production provenance 或外部效度。
- 最终协议单规则 Gemini API smoke 与三臂各一次 Qwen30B development smoke 已闭环，三臂均 5/5 完成且共同有效 5/5；formal gate 保持未判定。正式 60 规则/300 例生成和九格回放尚未运行，不能声称 Precision、Recall 或 FPR 改善。

## 正式与本地资产

Git 跟踪的源码、测试、catalog 和文档应能描述当前系统。以下目录故意不进入 Git：

- `data/`：源数据、开发集、validation 和后续 final test；
- `results/`：原始输出、trace、指标、日志和昂贵的 embedding/API 缓存；
- `private_docs/`：服务器地址、个人路径和协作记录；
- `.env`：本地 API 凭据，Git 忽略。

`results/` 不是正式结论的唯一来源。关键配置、catalog 指纹和指标必须同步到 `docs/` 或受版本控制的实验清单。

正式清单写入 `experiments/manifests/`。`run_physics_eval_pipeline.py` 自动记录 Git/源码/Prompt/conda、输入与输出 SHA，并在 validation/final 启动时拒绝 dirty worktree；development 允许 dirty，但必须如实记录。详细规范见 [`experiments/README.md`](../experiments/README.md)。

`data/` 和 `results/` 当前分别约 3.1 GB 和 693 MB，且都被 Git 忽略。因此实验室机器只执行 `git pull` 不能复现冻结实验；数据集、trace 和缓存必须通过 `rsync`、对象存储或等价的受控通道同步，并在受版本控制的清单中登记相对路径、大小和 SHA-256。GitHub 只同步源码、catalog、文档和清单。

## 清理边界

可以直接重新生成并定期清理：

- `__pycache__/`、`*.pyc`、`.DS_Store`；
- `results/test_tmp/`；
- 已确认没有对应运行进程的 `.pid`；
- 空日志和空目录。

不得仅因体积大而删除：

- `data/combined_language_only.json` 等源数据；
- 已冻结的 development、validation 或 final-test 数据；
- `results/` 中无法从其他文件恢复的 GT、trace 和汇总；
- 规则聚类的 embedding/API 缓存，除非已经确认无需续跑；
- `catalogs/` 中仍被正式流程或历史复现引用的文件。

## Catalog 边界

`catalogs/rules_unified_3000.json` 是当前 development 基线；`catalogs/rules_unified_3000_runtime_backfilled.json` 是已被效果消融否决的历史参考。两者是不同规则集合，目录整理不能合并、覆盖或按文件名推断它们等价；实验必须记录实际路径和 SHA-256。详细说明见[规则库说明](规则库说明.md)。

## 新文件放置规则

- 可复用运行逻辑进入 `core/`、`rules/`、`rule_framework/` 或 `symbolic/`，不要堆进一次性脚本。
- 当前流程的 CLI 放在 `scripts/`；只为复现旧实验服务的包装器和专用分析程序放在 `scripts/legacy/`。
- 自动化测试与最小数据进入 `tests/` 和 `tests/fixtures/`。
- 冻结实验的可提交 manifest 进入 `experiments/manifests/`，原始产物仍进入 `results/`。
- 动态状态写入[项目进展](项目进展.md)，评测事实写入[效果测评](效果测评.md)。
- 大型数据和运行产物分别进入 `data/`、`results/`，不要提交到 Git。
